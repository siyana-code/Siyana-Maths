# System Architecture — MVP

**Status:** Approved direction; implementation details to be validated in Phase 1
**Last updated:** 2026-09-23

## 1. Goals

- Serve a fast, mobile-friendly O/L Mathematics paper catalog.
- Store structured questions, Sinhala solutions, and full marking schemes.
- Link to existing YouTube, TikTok, and Facebook videos without hosting video files.
- Give one tutor/admin a safe publishing and contact-management workflow.
- Keep the first deployment inexpensive and upgradeable to paid hosting.
- Enforce authorization and validation on the server.

## 2. System boundaries

```text
Browser
  |
  | HTTPS
  v
Next.js on Vercel
  |
  | JSON/HTTPS + Supabase access token
  v
FastAPI on Render
  |
  | server-side Supabase access
  v
Supabase Auth + Postgres
  |
  +-- optional Storage later, not required for MVP
```

### Responsibilities

| Component | Responsibility |
|---|---|
| Next.js on Vercel | Public pages, admin UI, server rendering, SEO metadata, browser auth session, API orchestration |
| Supabase Auth | Admin authentication, tokens, account recovery, email confirmation |
| FastAPI on Render | Validation, authorization, domain workflows, URL normalization, public/admin APIs, contact abuse controls |
| Supabase Postgres | Papers, taxonomy, questions, answers, marking schemes, video sources, contact messages, site settings |
| External providers | Existing YouTube, TikTok, and Facebook video hosting |

The browser does not need direct privileged database access. The public Supabase key may exist in the frontend for Auth only; the service-role key is backend-only.

## 4. Request flows

### Public paper request

1. Vercel renders the catalog or paper route.
2. The frontend calls the public FastAPI endpoint with filter parameters.
3. FastAPI validates query parameters and asks the Supabase repository for published papers only.
4. The API returns a typed response with a request ID.
5. The frontend renders the page and metadata.

### Admin publish request

1. The admin signs in through Supabase Auth.
2. The frontend obtains a short-lived access token.
3. The frontend sends an authenticated mutation to FastAPI.
4. FastAPI verifies the JWT and loads the profile role.
5. FastAPI validates all paper/question/marking/video data.
6. The API writes transactionally and returns the updated resource.
7. The frontend refreshes the preview.

### Contact request

1. The browser submits a small contact payload.
2. FastAPI validates fields and rejects honeypot/spam patterns.
3. The API rate-limits the request and stores the message through the backend repository.
4. The public UI shows a neutral success state without exposing internal details.

## 5. Backend structure

### Modules

- `health` — liveness and readiness endpoints.
- `auth` — Supabase token verification and current-user role.
- `taxonomy` — levels, subjects, years, and topics.
- `papers` — public paper catalog and admin CRUD.
- `questions` — ordered question and solution workflow.
- `marking_scheme` — ordered method/award-note items and validation.
- `video_sources` — provider allowlist and URL normalization.
- `contact` — contact message submission and admin review.
- `site` — public contact/social settings.

### Technology

- Python 3.12 or the Render-supported runtime.
- FastAPI and Pydantic.
- Async Supabase/Postgres access.
- Ruff and Pytest.
- Versioned REST endpoints under `/api/v1`.
- OpenAPI generated by FastAPI as the contract source.

## 6. Frontend structure

- Next.js App Router.
- TypeScript strict mode.
- Server components for public catalog/detail pages where practical.
- Client components only for interactive filters, auth, and admin forms.
- Supabase SSR/client helpers for the admin session.
- Typed API client with centralized errors and request IDs.
- Controlled Markdown/math renderer for questions, solutions, and marking notes.
- Responsive CSS/design tokens before adding a large UI framework.

## 7. Content and video model

The primary content unit is an O/L Mathematics `paper`.

```text
Paper
├── Questions (ordered)
│   ├── Answer / Sinhala solution
│   ├── Marking-scheme items (ordered)
│   └── Optional question-level video sources
└── Optional paper-level video sources
```

A video source is attached to exactly one paper and may optionally target one question belonging to that paper. This allows a paper-level discussion plus short question-specific videos.

The backend generates provider embed URLs from validated source URLs. It does not accept arbitrary iframe URLs.

## 8. Deployment

### Render

- Web service running Uvicorn.
- Health check endpoint.
- Environment variables configured in Render.
- Start with the currently available tier; upgrade to a paid instance when cold starts, usage, or reliability become a problem.
- Never add a second managed database if Supabase is the system of record.

### Vercel

- Next.js project rooted at `apps/web`.
- Production API URL and public Supabase Auth variables set in Vercel.
- Preview origins explicitly handled by backend CORS configuration.

### Supabase

- Separate development/staging and production projects when practical.
- SQL migrations applied through a controlled CLI/deployment process.
- Auth redirect URLs configured for local, preview, and production frontend origins.
- RLS enabled before any real data is entered.
- Backups and retention configured before production content is considered important.

## 9. Cross-cutting concerns

- Validation at every HTTP and database boundary.
- Structured logs with request IDs and no secrets or contact content.
- Exact-origin CORS rather than wildcard production origins.
- Cache public published reads briefly, but never cache admin responses publicly.
- Use UTC timestamps and display localized dates in the frontend.
- Keep API/database contracts versioned and synchronized with migrations.
- Add health/readiness checks and basic error monitoring before launch.
